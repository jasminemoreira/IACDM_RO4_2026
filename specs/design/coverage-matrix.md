# Matriz de cobertura — crítica adversarial

Um registro por achado. Lentes universais (7) e condicionais ativadas (10) aplicadas a cada
um dos 10 módulos de V(1). Modo generativo: a pergunta feita foi "como este módulo falha?",
nunca "este desenho é bom?".

## Iteração 1 — V(1)

| id | module | lens | severity | description |
|------|--------|----------|----------|-------------|
| ASS-01 | app | Assumptions | 🟡 | A-1 supõe primeira carga online, mas nada informa o usuário: abrir o app pela primeira vez offline dá página morta sem explicação. A premissa está declarada no documento e ausente do produto |
| ASS-02 | review-log | Assumptions | 🔴 | `at = max(agora, últimoAt+1)` supõe leitura de `últimoAt` serializada, mas `storage` é assíncrono. Dois `append` em voo (duplo clique, ou nota seguida de sync) leem o mesmo `últimoAt`, geram o mesmo `at`, logo o mesmo `eventId` — e a união, que deduplica por `eventId`, **descarta uma das duas revisões**. Viola o critério 2 do I3 dentro de uma única réplica |
| ASS-03 | sync | Assumptions | 🔴 | `pull(since)` supõe que `at` cresce com a chegada, o que é falso entre réplicas: um evento vindo de B pode ter `at` MENOR que a marca d'água local (B estava offline, ou tem relógio atrasado). Pedir `since = últimoAtLocal` **pula permanentemente** esses eventos — eles nunca mais serão buscados |
| ASS-04 | scheduler | Assumptions | 🟢 | `I` dias → ms por ×86 400 000 supõe dia uniforme, ignorando horário de verão e segundo bissexto. Coerente com a decisão de instante exato da Fase 0, mas a premissa não está escrita ao lado da fórmula |
| ASS-05 | storage | Assumptions | 🟡 | A-7 diz que o armazenamento local não é durável, e o desenho supõe que o usuário sincroniza antes do despejo. Se o despejo vier antes da primeira sincronização, perde-se tudo — e nada no produto avisa que o progresso ainda só existe localmente |
| ASS-06 | session | Assumptions | 🟢 | A fila é apurada na abertura e não reavaliada: um cartão que vence no meio da sessão não entra nela. É o que garante a terminação (critério 3 do I1), mas é premissa não declarada |
| ARQ-01 | ui | Architectural | 🔴 | Ciclo de dependência declarado na própria tabela de V(1): `ui` depende-de `app` e `app` depende-de `ui`. Nenhum dos dois pode ser testado nem substituído isoladamente, e a raiz de composição deixa de ser raiz |
| ARQ-02 | app | Architectural | 🟢 | `app` depende de todos os 7 módulos restantes. Legítimo para raiz de composição, mas é o único ponto onde uma mudança de contrato se propaga inteira |
| ARQ-03 | server | Architectural | 🟡 | `POST /events` tem semântica de união idempotente por `eventId`, o que exige a mesma lógica de `review-log.merge` — mas `server` declara `depends-on: —`. Ou duplica a lógica (e as duas cópias divergem com o tempo) ou a dependência está faltando na tabela |
| ARQ-04 | service-worker | Architectural | 🟡 | A lista de precache tem de enumerar os arquivos ESM produzidos pelo build, e nenhum módulo declara a responsabilidade de gerá-la. Escrita à mão, ela silenciosamente desatualiza a cada módulo novo — e o casco incompleto só falha offline, onde ninguém está olhando |
| IMP-01 | deck | Implementability | 🔴 | `versionOf(deck) -> string` é síncrona, mas a única API de hash do navegador é `crypto.subtle.digest`, que é **assíncrona** e só existe em contexto seguro. O contrato, como declarado, não é implementável |
| IMP-02 | app | Implementability | 🟡 | `start(ports)` não enumera `ports`. Não dá para codificar `app` numa sessão dedicada sem inventar o contrato que ele recebe — exatamente o que a granularidade da Fase 1 deveria evitar |
| IMP-03 | app | Implementability | 🔴 | Ninguém declara que a nota só avança a tela **depois** do `append` confirmado. Com `storage` assíncrono, a ordem natural (renderiza, depois grava) perde a revisão se a escrita falhar — e o usuário viu a tela avançar, então não repete a nota |
| IMP-04 | session | Implementability | 🟡 | `open` promete "ordem determinística" da fila sem dizer por qual chave. Duas implementações corretas do contrato apresentam os cartões em ordens diferentes |
| SCI-01 | scheduler | Scientific | 🟢 | A §4 escreve `round` sem fixar o desempate de 0,5. `Math.round` do JS arredonda para +∞; meia-par daria outro intervalo. O valor não tem fonte porque a fonte não o especifica — cabe fixar e documentar |
| SCI-02 | review-log | Scientific | 🟡 | A afirmação "qualquer serialização determinística de eventos concorrentes é legítima" sustenta a decisão central de reconciliação e **não tem citação**. É raciocínio próprio apoiado em Saito & Shapiro, não algo que a fonte afirme |
| SEC-01 | server | Security | 🔴 | `POST /events` sem autenticação nem verificação de origem. Qualquer processo da máquina — e qualquer página web aberta no navegador, via requisição a `localhost` — lê o log de estudo inteiro e injeta eventos. A §3 exclui autenticação **de usuário**, não torna o endpoint público |
| SEC-02 | server | Security | 🔴 | Servir estáticos por concatenação de caminho permite travessia de diretório: `GET /../../etc/passwd`. O servidor roda com as permissões do usuário |
| SEC-03 | ui | Security | 🟡 | `hanzi`/`pinyin`/`gloss` vêm de um arquivo declarado como **entrada** e vão para o DOM. Inseridos por `innerHTML`, um deck trocado executa script na origem do app — e essa origem contém o log inteiro |
| SEC-04 | server | Security | 🟡 | Corpo de `POST` sem limite de tamanho: um único pedido esgota a memória do processo |
| SEC-05 | sync | Security | 🟡 | I-2 valida `q` na fronteira, mas nada valida `at` nem `replicaId` vindos do remoto. Um `at` no ano 9999 entra no log e envenena `últimoAt` para sempre (ver CTL-03) |
| PERF-01 | review-log | Performance | 🟡 | Não está declarado quando `fold` roda. Redobrar o log a cada nota dá O(N) por nota e O(N²) por sessão — e N cresce para sempre |
| PERF-02 | review-log | Performance | 🟡 | A-6 justifica o replay integral pelo tamanho do **deck** (centenas a milhares de cartões), mas o custo é governado pelo número de **eventos**, que cresce com o uso e não com o deck. A premissa mede a grandeza errada |
| PERF-03 | sync | Performance | 🟡 | duplica: ASS-03 — se `since` não é confiável, a única sincronização correta é puxar tudo, sempre |
| REG-01 | app | Regulatory | 🟢 | A §2 exige módulos como diretórios de primeiro nível com ponto de entrada explícito. Nada verifica isso: a conformidade depende de disciplina, e um `import` para dentro de outro módulo passa despercebido |
| REG-02 | app | Regulatory | 🟢 | A §7 (comitar a cada passo com significado próprio) é requisito normativo sem dono nem verificação |
| REG-03 | service-worker | Regulatory | 🟡 | A §1 pede uma **aplicação web progressiva**, o que implica instalabilidade: manifest e ícone. Eles aparecem na lista de precache, mas nenhum módulo declara produzi-los |
| RES-01 | sync | Resilience | 🟡 | Falha de rede não tem política declarada: não há repetição, não há fila de pendências, não há registro do que ficou por enviar. `synchronize` simplesmente rejeita |
| RES-02 | sync | Resilience | 🔴 | `POST /events -> {accepted: n}` não diz **quais** eventos entraram. Se o servidor aceitar 3 de 5 e o cliente marcar todos como enviados, os 2 restantes nunca são reenviados: revisões existentes localmente somem do remoto e do outro dispositivo |
| RES-03 | server | Resilience | 🔴 | Persistência em arquivo JSON sem escrita atômica: uma queda no meio do `write` deixa JSON truncado, e o remoto inteiro — a rede de segurança contra o despejo do navegador (A-7) — vira ilegível |
| RES-04 | storage | Resilience | 🟡 | `indexedDB.open` falha em modo privado, com cota esgotada ou com o banco corrompido. Nenhum caminho alternativo declarado: o app fica inutilizável sem dizer por quê |
| UX-01 | ui | UI/UX | 🟡 | Seis botões de 0 a 5 sem a semântica da escala. Sem saber que 3 é "correto com dificuldade séria" e 2 é "errado", o usuário nota por intuição — e a nota é a **única** entrada do algoritmo. Erro de calibração corrompe todo o agendamento |
| UX-02 | ui | UI/UX | 🟡 | Nenhum estado visível de sincronização ou de rede. O usuário revisa uma semana offline acreditando que o progresso está salvo no remoto |
| UX-03 | ui | UI/UX | 🟡 | Sessão vazia (nada devido) é resultado válido e frequente — é o estado normal entre revisões — e não há tela declarada para ele. Sem isso, parece defeito |
| UX-04 | ui | UI/UX | 🟢 | Nenhuma declaração de teclado ou acessibilidade para os seis botões de nota, que são o gesto repetido dezenas de vezes por sessão |
| MIG-01 | storage | Migration / Coexistence | 🟡 | O esquema do IndexedDB não tem versão nem caminho de `upgrade` declarado. Mudar o store `events` numa versão futura quebra quem já tem dados — e o dado é justamente o que não pode se perder |
| MIG-02 | service-worker | Migration / Coexistence | 🔴 | Cache-first sem versionar o cache nem limpar os antigos no `activate`: depois do primeiro deploy o usuário fica preso à versão velha para sempre. Uma correção — inclusive das críticas desta matriz — nunca chega a quem já instalou |
| MIG-03 | deck | Migration / Coexistence | 🟢 | Versão por hash do conteúdo: reindentar o JSON muda a versão sem mudar o conteúdo. Dispara migração espúria — inofensiva, porque a migração não move progresso |
| SUS-01 | review-log | Sustainability / Proportionality | 🟡 | duplica: PERF-02 — não compactar o log é decisão declarada, mas apoiada numa premissa sobre tamanho de deck; sem teto declarado nem medição, ninguém sabe quando deixa de valer |
| SUS-02 | server | Sustainability / Proportionality | 🟡 | Reescrever o arquivo JSON inteiro a cada `POST` custa O(N) por evento e O(N²) na vida do projeto, para gravar um registro de ~120 bytes |
| PRO-01 | sync | Process / Workflow | 🟡 | `synchronize` não tem máquina de estados. Duas invocações concorrentes (clique duplo, ou automática mais manual) se sobrepõem e ambas gravam |
| PRO-02 | app | Process / Workflow | 🟡 | Não está declarado **quando** a versão do deck é comparada. Se a troca for detectada no meio de uma sessão, a fila aberta referencia ids que saíram do conjunto ativo |
| PRO-03 | app | Process / Workflow | 🟡 | duplica: ASS-01 — o caminho de exceção "primeira carga sem rede e sem cache" não existe no fluxo |
| GOV-01 | server | Governance / Accountability | 🟡 | A-11 mantém um único espaço de progresso. Dois estudantes que apontem para o mesmo servidor têm os logs fundidos de forma silenciosa e irreversível: `replicaId` atribui a um **aparelho**, nunca a uma pessoa, e não há como separar depois |
| GOV-02 | review-log | Governance / Accountability | 🟢 | Limpar o armazenamento gera novo `replicaId`: os eventos antigos ficam atribuídos a um aparelho que não existe mais, sem vínculo com o novo |
| OBS-01 | app | Observability / Operability | 🟡 | Nenhum diagnóstico. "Meu cartão não apareceu" e "a sincronização não trouxe nada" só se investigam alterando o código — e o estado que explicaria (fila apurada, últimoAt, eventos pendentes) não é exposto em lugar nenhum |
| OBS-02 | service-worker | Observability / Operability | 🟡 | Não há como saber qual versão do casco está ativa nem se o service worker chegou a instalar. O sintoma de falha (app velho, ou app que não abre offline) aparece justamente quando não há ferramenta à mão |
| OBS-03 | server | Observability / Operability | 🟢 | Nenhum registro de requisição: um evento que se perdeu no caminho não deixa rastro de qual lado o perdeu |
| CTL-01 | scheduler | Control Engineering | 🟢 | O SM-2 é um controlador com realimentação, e no piso do `EF` ele deixa de regular: falhas repetidas travam em `EF=1.3` e `I=1`, e o cartão volta todo dia para sempre sem convergir. É comportamento da fonte, congelado pela §4 — registrar, não corrigir |
| CTL-02 | sync | Control Engineering | 🟢 | duplica: RES-01 — sem política de repetição declarada, qualquer repetição futura em temporizador vira tempestade de tentativas contra um servidor fora do ar |
| CTL-03 | review-log | Control Engineering | 🔴 | `at = max(agora, últimoAt+1)` é um integrador sem anti-windup. Um único evento com `at` no futuro — relógio adiantado, ou vindo do remoto sem validação (SEC-05) — trava `últimoAt` no futuro **para sempre**: todos os eventos seguintes recebem carimbos futuros, e `dueAt`, que compara com o `agora` real, deixa de vencer cartão nenhum |
| LIN-01 | server | Linguistics / Grammar | 🟡 | `GET /events?since=<at>` não diz se `since` é inclusivo ou exclusivo. Duas implementações corretas do contrato divergem, e na leitura exclusiva os eventos com `at` igual à marca d'água somem |
| LIN-02 | review-log | Linguistics / Grammar | 🟡 | `orderKey` desempata por `replicaId`, uma string, sem fixar a comparação. `<` compara por unidade de código, `localeCompare` compara por regra de locale: duas réplicas podem ordenar o mesmo conjunto de forma diferente — e aí a dobra diverge, que é exatamente o que a ordem total existia para impedir |
| LIN-03 | storage | Linguistics / Grammar | 🟢 | `deckVersion() -> string \| null` não distingue "nunca definido" de "definido como vazio" |
| LIN-04 | server | Linguistics / Grammar | 🟡 | duplica: RES-02 — `accepted: number` é ambíguo entre recebidos, gravados e novos após deduplicação, e a decisão do cliente depende de qual dos três é |
| MEC-01 | storage | Mechanical Engineering | 🟡 | duplica: RES-04 — o desenho tolera um único comportamento de IndexedDB; modo privado, Safari e cota esgotada variam, e nenhuma variação está prevista |
| MEC-02 | scheduler | Mechanical Engineering | 🟡 | `EF` acumula em ponto flutuante: a mesma sequência dá 2.4600000000000004, não 2.46. A igualdade entre réplicas só se sustenta se a sequência for idêntica **e** nada arredondar no caminho — um `toFixed` na serialização quebra a convergência sem que nada acuse |
| MEC-03 | deck | Mechanical Engineering | 🟡 | duplica: MIG-03 — o hash depende da serialização exata; dois produtores do mesmo deck com espaçamento ou ordem de chaves diferentes geram versões diferentes para conteúdo idêntico |
| MEC-04 | server | Mechanical Engineering | 🟡 | A pilha depende de Node com remoção nativa de tipos (≥ 22.6, estável a partir da 23.6) e a verificação foi feita na 24.13. Nada declara essa faixa: na Node 20 o projeto inteiro não roda, com erro de sintaxe incompreensível |

## Iteração 2 — V(2)

Segunda passagem, contra a arquitetura revisada. Foco nos quatro mecanismos que V(2)
introduziu e que nenhuma lente tinha visto — alocação atômica de `seq`, cursor `sseq`, JSONL,
inversão de dependência — e reexame de tudo o mais.

| id | module | lens | severity | description |
|------|--------|----------|----------|-------------|
| ASS-07 | storage | Assumptions | 🔴 | O contrato de V(2) tem `append(draft)` para evento local e **nenhum caminho para gravar evento vindo do remoto**. `sync` puxa eventos e não tem onde pô-los; usar `append` recarimbaria identidade alheia com `seq` local, destruindo o `eventId` de origem. O log deixa de ser a união que a reconciliação pressupõe |
| ASS-08 | storage | Assumptions | 🔴 | `seq` vem do `autoIncrement` do store, que **reinicia em 1** se o store for recriado (limpeza, `onupgradeneeded` que apague, despejo parcial). Com o mesmo `replicaId` preservado em `meta`, os eventos novos nascem com `eventId` já usados — e `review-log.merge`, que deduplica por `eventId`, **descarta os novos em silêncio**. A premissa A-5 garante unicidade do `replicaId`, nunca a do par `(replicaId, seq)` ao longo do tempo |
| ASS-09 | sync | Assumptions | 🟡 | Supõe que o `sseq` do servidor nunca retrocede. Restaurar o arquivo de um backup mais velho deixa todo cliente com marca d'água à frente do servidor: os eventos reemitidos nunca mais são puxados |
| ASS-10 | app | Assumptions | 🟡 | O caminho de exceção criado para A-1 não distingue "primeira carga sem rede" de "falha de rede qualquer" — a mesma tela para duas situações com saídas diferentes |
| ASS-11 | event-store | Assumptions | 🟡 | Supõe processo único. Duas instâncias do servidor sobre o mesmo arquivo intercalam appends e atribuem `sseq` duplicado, sem que nada detecte |
| ARQ-05 | event-store | Architectural | 🟡 | `event-store` depende de `review-log`, que é módulo do núcleo do navegador. O servidor passa a importar código do cliente e a fronteira de implantação — o que é servido e o que roda em Node — não está declarada em lugar nenhum |
| ARQ-06 | session | Architectural | 🟡 | A correção de IMP-03 é **prosa, não estrutura**: `grade(s,q,at)` já devolve a sessão avançada, então nada no contrato impede renderizar antes do `append` confirmado. Estruturalmente resolvido seria separar `grade -> draft` de `commit(session, evento) -> session`, tornando impossível avançar sem o evento gravado |
| IMP-05 | app | Implementability | 🟡 | Os `Ports` foram enumerados, mas a **sequência de arranque** (carregar deck → conferir versão → dobrar log → abrir sessão → montar interface) não está escrita. Codificar `app` numa sessão dedicada ainda exige inventá-la |
| IMP-06 | event-store | Implementability | 🟡 | Módulo novo sem contrato de erro: não está dito o que `append` devolve com disco cheio, arquivo sem permissão ou diretório inexistente |
| SCI-03 | deck | Scientific | 🟡 | FNV-1a entrou em V(2) **sem fonte citada**, violando a regra do próprio projeto — nenhum algoritmo sem referência verificável. É exatamente o tipo de troca plausível que a regra existe para pegar |
| SEC-06 | event-store | Security | 🟡 | O contrato não declara que o servidor **re-serializa** o evento antes de gravar. Ecoar bytes do cliente na linha do JSONL permite quebrar o enquadramento e injetar registros |
| SEC-07 | event-store | Security | 🟡 | duplica: SEC-01 — nada impede um cliente de forjar o `replicaId` de outro aparelho e injetar eventos atribuídos a ele |
| SEC-08 | server | Security | 🟡 | A verificação de `Origin` não decide o caso sem cabeçalho: navegações e clientes não-navegador não enviam `Origin`. Rejeitar quebra o app; aceitar reabre o buraco que SEC-01 fechou |
| PERF-04 | event-store | Performance | 🟡 | `after(sseq)` sobre JSONL varre o arquivo desde o início a cada sincronização. Sem índice, o custo de puxar nada cresce com todo o histórico |
| PERF-05 | app | Performance | 🟡 | A nota aplica `applyOne` incremental sobre o estado corrente; se uma sincronização estiver em voo e trouxer eventos com `at` anterior, o incremento fica sobre base que a fusão invalida |
| REG-04 | event-store | Regulatory | 🟢 | O critério 3 do I3 (cenário reproduzível) agora envolve dois processos, e nenhum módulo declara o roteiro executável que o encena |
| RES-05 | sync | Resilience | 🟡 | Não está declarada a ordem entre gravar os eventos puxados e avançar a marca d'água. Gravar depois de avançar perde tudo o que estava em voo numa queda |
| RES-06 | event-store | Resilience | 🔴 | `appendFile` sem `fsync`: o servidor responde `{stored: [...]}`, o cliente avança a marca d'água e **nunca reenvia** — mas o dado ainda está no buffer do sistema. Uma queda de energia apaga eventos que o cliente considera entregues, e ninguém os reenvia. É perda de revisão pela porta que V(2) abriu ao tornar o `stored` autoritativo |
| RES-07 | event-store | Resilience | 🟡 | Duas chamadas de `appendFile` em voo no mesmo processo podem intercalar escritas acima do tamanho atômico do sistema, corrompendo linhas no **meio** do arquivo — não só a última. Falta declarar fila serializada de escrita |
| UX-05 | ui | UI/UX | 🟡 | `render(viewModel)` redesenha tudo: o foco de teclado e o estado "revelado" se perdem a cada quadro, justamente no gesto que se repete dezenas de vezes por sessão |
| MIG-04 | service-worker | Migration / Coexistence | 🟡 | `skipWaiting` + `clients.claim` trocam o service worker **sob uma página em execução**: o JS velho continua rodando e passa a buscar recursos do cache novo. A correção de MIG-02 criou a janela de incompatibilidade clássica |
| SUS-03 | event-store | Sustainability / Proportionality | 🟢 | O arquivo do servidor cresce para sempre, como o log do cliente. A decisão de não compactar, aceita para o cliente, agora vale em dois lugares e nenhum deles a mede |
| PRO-04 | app | Process / Workflow | 🟡 | A versão do deck passa a ser conferida só no arranque (correção de PRO-02), o que deixa sem resposta a aba aberta por dias: a troca de versão no meio da vida da página não tem caminho declarado |
| GOV-03 | event-store | Governance / Accountability | 🟢 | `sseq` é atribuído pelo servidor e o cliente não tem como auditá-lo: não há prova, do lado de quem enviou, de que um evento foi mesmo aceito e ordenado |
| OBS-04 | event-store | Observability / Operability | 🟡 | A linha truncada é descartada **em silêncio** na leitura. O arquivo perde conteúdo e nada registra que perdeu — a única evidência some junto com o dado |
| CTL-04 | sync | Control Engineering | 🟢 | A decisão de não repetir automaticamente (correção de RES-01) deixa o sistema sem laço fechado: se o usuário nunca acionar a sincronização, as pendências crescem sem realimentação alguma |
| LIN-05 | ui | Linguistics / Grammar | 🟡 | `ViewModel` é nomeado no contrato de `ui` e nunca declarado. Sem ele, `ui` e `app` não podem ser construídos em sessões separadas — que é a razão de a inversão de dependência ter sido feita |
| LIN-06 | sync | Linguistics / Grammar | 🟡 | duplica: LIN-05 — `SyncReport` nomeado no contrato e não declarado |
| LIN-07 | app | Linguistics / Grammar | 🟡 | duplica: LIN-05 — `Diagnostico` nomeado no contrato e não declarado |
| LIN-08 | event-store | Linguistics / Grammar | 🟡 | `append(events) -> {stored}` não diz se `stored` inclui os eventos **já conhecidos** (deduplicados) ou só os novos. O cliente precisa dos dois casos como "entregue" para avançar a marca d'água; a leitura errada faz reenviar para sempre |
| MEC-05 | storage | Mechanical Engineering | 🟡 | A queda para adaptador em memória muda a durabilidade sem mudar o contrato: `mode()` existe, mas nada obriga o chamador a olhar. O sistema segue funcionando e perdendo tudo a cada recarga |
| MEC-06 | event-store | Mechanical Engineering | 🟡 | `appendFile` não garante atomicidade em sistema de arquivos de rede, nem para linhas curtas. O desenho tolera apenas disco local |
